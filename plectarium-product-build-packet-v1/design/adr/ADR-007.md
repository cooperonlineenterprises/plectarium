# ADR-007: Internal contract foundation and canonical encoding

**Status:** Accepted under current PLEC-FND-002 continuation  
**Decision:** PLEC-021

The first internal library uses Python and explicit schema bytes with exact IDs,
versions and SHA-256 pins. References resolve only within the supplied registry;
there is no network retrieval, latest-version fallback or automatic migration.
Unknown breaking versions fail. Trusted migration functions must be explicitly
registered for an exact source/target pair and validated on both sides.

`plectarium.canonical-json.v1` encodes null, booleans, strings, lists, string-keyed
objects and integers in the inclusive range -(2^53-1) through 2^53-1. Encode as
UTF-8 JSON, keys sorted by Unicode code point, no insignificant whitespace, no
ASCII escaping and no trailing newline. Preserve Unicode exactly; reject lone
surrogates, cycles, floats and non-JSON values. Limits are explicit and bounded.
JSON/YAML parsing and schema validation can accept finite fractional numbers;
this initial identity profile refuses to canonicalize them. External domain
payloads remain opaque bytes and use raw-byte SHA-256 without reserialization.

The internal version label must accompany a canonical receipt; the digest is
SHA-256 of those exact encoded bytes. This is not RFC 8785/JCS, a family contract
change, or a production wire interoperability promise. Future encoding changes
need an explicit successor and migration; old identities remain bound to old
bytes and rules. Existing suite/family schema IDs and bytes are unchanged.

Schema validation proves structural conformity only. Approval, tenant isolation,
permission subsets, freshness, execution profiles and other cross-record rules
remain with their owning S1 tasks. An internal schema receipt grants no authority.
